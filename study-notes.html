4. DB 설계와 RLS

요청: "백엔드를 구축하자. 민감 정보는 환경변수로 저장하고 RLS를 적용할 건데, 먼저 DB 구조를 설계해야겠지?"

결정한 것

항목결정
로그인 방식이메일 + 비밀번호 (Google은 나중에)
이메일 인증지금은 끄고 나중에 켜기 (무료 플랜 메일 발송 한도가 작음)
기구 데이터DB로 옮기지 않고 코드에 유지

테이블

테이블용도포인트
profiles닉네임가입 시 트리거로 자동 생성
favorites즐겨찾기(user_id, equipment_id) 기본키로 중복 방지
workout_logs운동 기록무게 > 0, 횟수·세트 ≥ 1, 메모 100자 이하를 DB 제약조건으로도 검사

SQL: supabase/migrations/20261103000000_init.sql

RLS 정책의 기본 형태

alter table public.favorites enable row level security;
revoke all on table public.favorites from anon;  -- 비로그인은 아예 접근 불가

create policy "favorites: 본인 조회"
  on public.favorites for select to authenticated
  using ((select auth.uid()) = user_id);

배운 개념

  • RLS(Row Level Security): 테이블의 "행" 단위로 누가 읽고 쓸 수 있는지 DB가 직접 검사한다. 앱 코드에 버그가 있어도 DB가 막아 준다.
  • using은 기존 행을 읽거나 고칠 때의 조건, with check는 새로 넣거나 바뀐 행이 지켜야 할 조건이다.
  • auth.uid()를 (select auth.uid())로 감싸면 행마다 다시 계산하지 않아 빠르다.
  • 필요 없는 동작은 정책을 만들지 않는다. (즐겨찾기는 수정할 일이 없어 update 정책 없음)
  • security definer 함수(관리자 권한으로 실행)는 API로 직접 호출하지 못하게 실행 권한을 회수한다.

환경변수와 키

변수브라우저 노출설명
NEXT_PUBLIC_SUPABASE_URL괜찮음프로젝트 주소
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY괜찮음공개 키. 데이터 보호는 RLS가 담당
Secret key (sb_secret_, service_role)절대 안 됨RLS를 무시하는 관리자 키. 사용하지 않음
  • 사용자 비밀번호는 우리 DB에도 환경변수에도 없다. Supabase Auth가 해시로 따로 관리한다.
  • .env.local은 .gitignore에 포함되어 커밋되지 않는다. 예시는 .env.example로 공유한다.
  • NEXT_PUBLIC_이 붙은 변수만 브라우저 코드에 들어간다.

5. 로그인과 데이터 연동

요청: "지금까지 내용 커밋 먼저 하고 로그인, 데이터 연동 코드 작성해줘"

구조

  • 로그인과 데이터 조회는 브라우저에서 Supabase로 직접 한다.
    • 서버에서 세션(쿠키)을 읽으면 Cache Components 때문에 정적 페이지가 깨진다.
    • 공개 키가 브라우저에 있어도 RLS가 본인 데이터만 허용하므로 안전하다.
  • lib/storage/favorites.ts, logs.ts: 로그인 전은 localStorage, 로그인 후는 Supabase
  • 처음 로그인하면 이 기기에 있던 데이터를 계정으로 옮긴다. 실패하면 남겨 두고 다음에 다시 시도한다.
  • 즐겨찾기는 화면을 먼저 바꾸고, 서버 저장에 실패하면 되돌린다. (낙관적 업데이트)
  • 환경변수가 없으면 오류 없이 localStorage 모드로 동작한다.
  • Supabase의 영어 오류 메시지를 한국어로 바꿔 보여준다.

배운 것

  • 저장소를 한곳에 모아 둔 덕분에 화면 코드는 거의 고치지 않고 백엔드를 붙였다.
  • 코드가 정상 동작해도, 실제 Supabase 프로젝트로 확인하기 전까지는 "검증 안 됨"이라고 구분해야 한다.

8. 기구 사진과 운동 자세 그림

요청: "체스트 프레스, 펙덱 플라이, 플랫 벤치프레스 3개만 기구 이미지와 운동 자세 이미지를 넣고 싶어"

과정

  1. Unsplash에서 무료 라이선스 사진을 찾아봤지만, 기구만 찍힌 사진이 없었고 펙덱은 검색 결과가 0건이었다.
  2. → 사진을 직접 제공하기로 바꿨다.
  3. 정해진 경로에 넣기: public/images/equipment/<slug>.jpg, public/images/posture/<slug>.jpg

화면 처리

  • 상세 화면: 기구 사진은 잘리지 않게 전체 표시 (object-contain)
  • 목록 썸네일: 가로 사진이 작게 보여서 가운데를 채우게 표시 (object-cover)
  • 자세 그림: "운동 자세" 설명 위에 넣고, 누르면 원본 크기로 열림

배운 것

  • 무료 이미지는 라이선스(Unsplash+ 유료 제외)와 출처 표기를 확인해야 한다.
  • 원하는 사진이 없으면 직접 준비하는 게 가장 정확하고 저작권 걱정도 없다.
  • 파일 확장자(.jpg)와 실제 형식(PNG)이 달라도 브라우저와 Next.js는 내용을 보고 처리한다. 그래도 맞추는 게 좋다.
  • 사진이 없는 기구는 주동근을 강조한 인체 그림으로 대신 보여주게 해서, 일부만 있어도 화면이 어색하지 않다.

9. Vercel 배포

요청: "배포는 무료로 하고 싶은데 가능해?" → Hobby 플랜(개인·비상업적 용도 무료)

순서

  1. https://vercel.com/new 에서 GitHub 저장소 Import ("Add New"가 안 보이면 이 주소로 바로 이동)
  2. Deploy 전에 Environment Variables에 .env.local의 두 값 등록 (Secret key는 넣지 않음)
  3. Deploy → https://ai-agent-mainquest1-health.vercel.app
  4. Supabase Authentication → URL Configuration의 Site URL을 배포 주소로 등록 (권장)

배포 후 확인한 것

  • 모든 페이지 200, 없는 주소 404, 사진 정상
  • 환경변수 적용: 내 정보 화면에 로그인 폼이 나옴
  • 배포된 JavaScript에 공개 키만 있는지 직접 열어 확인. sb_secret_ 글자는 라이브러리의 키 종류 구분 코드였다.

배운 것

  • main에 푸시하면 Vercel이 자동으로 다시 배포한다.
  • 환경변수를 빼먹어도 사이트는 열리지만 로그인이 안 된다. (앱이 localStorage 모드로 동작하게 만들어 둔 덕분)
  • Supabase 무료 프로젝트는 일주일 정도 사용이 없으면 일시 정지될 수 있다.

자주 쓴 명령

npm run lint     # 코드 검사

git status --short
git add <파일> && git commit -m "메시지" && git push
  • 개발 서버가 켜진 상태에서 npm run build를 하면 .next 폴더가 겹쳐 개발 서버가 꼬일 수 있다. 빌드 전에 개발 서버를 멈춘다.
  • .env.local을 바꾼 뒤에는 개발 서버를 다시 시작해야 적용된다.

Claude Code에 요청할 때 효과적이었던 방식

  • "먼저 인터뷰해 줘, 한 번에 하나씩": 요구사항을 빠짐없이 정리할 수 있었다.
  • "아직 정하지 않은 건 따로 표시해 줘": 결정을 미뤄도 진행이 막히지 않았다.
  • "먼저 DB 구조를 설계해야겠지?": 구현 전에 설계를 확인하고 넘어갈 수 있었다.
  • "커밋 먼저 하고 ~해 줘": 단계마다 되돌아갈 지점이 생겼다.
  • 큰 기능은 "방법을 먼저 물어보고" 선택지 중에서 고르니 결과가 예측 가능했다. (MCP 읽기 전용, 이메일 인증 끄기 등)
  • 결과를 직접 화면에서 확인하고 이상한 점을 바로 알려주니 수정이 빨랐다.
