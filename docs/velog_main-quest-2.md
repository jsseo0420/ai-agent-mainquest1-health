## 1. 왜 만들었나

헬스장에 등록하면 체성분 검사를 받는다. 그런데 결과지를 받아도 막막했다.

1. **숫자가 너무 많다.** 골격근량, 체지방률, 복부지방률에 표준 범위 숫자까지 한 장에 수십 개다.
2. **옮겨 적기 귀찮다.** 핵심 수치 8개만 손으로 옮겨도 2분쯤 걸리고 오타가 난다.
3. **운동으로 이어지지 않는다.** "체지방률이 높다"는 건 알겠는데, 그래서 어떤 기구로 뭘 해야 하지?
4. **챗봇 추천은 내 환경과 안 맞는다.** ChatGPT에 물어보면 도감에 없는 운동을 추천해서 자세를 확인할 수가 없다.

그래서 이런 가설을 세웠다.

> 결과지 사진으로 수치를 자동 추출하고, **헬스도감에 있는 운동만으로** 루틴을 짜 주면, 입력 시간은 크게 줄고 추천된 모든 운동의 자세를 도감에서 바로 확인할 수 있다.

성공 기준도 미리 숫자로 정했다.

| 항목 | 목표 |
|---|---|
| 핵심 8개 필드 추출 정확도 | 95% 이상 |
| 입력 시간 (사진 → 수치) | 10초 이내 (수기 약 2분) |
| 추천 운동의 도감 포함률 | 100% |

## 2. 데이터: 실제 결과지는 쓰지 않았다

체성분 결과는 **개인 건강정보**다. 내 것이라도 공개 저장소에 올리고 싶지 않았다. 그래서 **가상 결과지를 직접 만들었다.**

- Node.js + puppeteer로 HTML 양식을 이미지로 찍어 **15장 + 정답 JSON** 생성
- 특정 브랜드 양식을 베끼지 않은 **자체 양식**
- 실제 결과지처럼 **헷갈리는 숫자**를 일부러 넣음: 표준 범위, 적정체중, 지방·근육 조절값, 권장섭취열량
- 15장 중 11장에는 **기울기·흐림·그림자·저해상도**를 넣어 폰 촬영을 흉내 냄

시드 기반으로 만들어서, 나중에 "모델이 틀린 숫자가 결과지의 어느 숫자였는지"를 역추적할 수 있었다. 이게 실패 분석에서 꽤 유용했다.

## 3. 수치 추출: OCR 모델 vs VLM

세 가지 방식을 Colab에서 같은 15장으로 비교했다.

| 방식 | 구성 |
|---|---|
| A. OCR 모델 | EasyOCR로 글자를 읽고, "라벨 오른쪽 숫자"를 규칙으로 고른다 |
| B. VLM (API) | Gemini Flash에 이미지를 주고 JSON 스키마로 받는다 |
| C. VLM (로컬) | Qwen2.5-VL 3B를 Colab T4 GPU에서 직접 돌린다 |

### 결과

| 방식 | 필드 정확도 | 장당 시간 (중앙값) | 사진 외부 전송 |
|---|---|---|---|
| A. EasyOCR + 규칙 | 40.8% | 1.7초 | 없음 |
| **B. Gemini Flash** | **100%** | 19.3초 | 있음 |
| C. Qwen2.5-VL 3B | 77.5% | 5.5초 | 없음 |

촬영 상태별로 보면 차이가 더 확실하다.

| 상태 | A | B | C |
|---|---|---|---|
| 깨끗함 | 100% | 100% | 62% |
| 기울기 | 25% | 100% | 92% |
| 흐림 | **0%** | 100% | 83% |
| 저해상도 | **0%** | 100% | 56% |

### OCR만으로는 결과지를 "해석"할 수 없었다

처음에는 OCR 모델로 결과지를 읽는 걸 생각했다. 그런데 결과를 보니 문제는 **글자 읽기가 아니라 숫자 고르기**였다.

- OCR은 "체중", "73.0", "61.9 ~ 76.6" 같은 **글자 조각**을 준다.
- 이 중 어느 게 측정값인지는 **사람이 짠 규칙**이 골라야 한다.
- 사진이 조금만 기울거나 흐려도 규칙이 무너져서, 틀린 71개 중 **59개가 값을 아예 찾지 못한 경우**였다.

Gemini 같은 **VLM(비전 언어 모델)은 OCR 능력이 모델 안에 들어 있어서**, 글자 읽기와 표·그래프 구조 이해를 한 번에 한다. 그래서 결론은 이렇게 났다.

> **OCR 모델만으로는 결과지를 해석할 수 없어서, OCR 능력이 내장된 VLM인 Gemini를 채택했다.**

## 4. 루틴 추천: LLM에게 맡길 것과 맡기지 않을 것

루틴 추천에서 가장 신경 쓴 건 **역할 나누기**였다.

```
수치 8개 + 성별
 → ① 코드가 판정 (표준보다 높은지 낮은지)
 → ② 코드가 목표 결정
 → ③ LLM이 도감 운동 목록 안에서 루틴 구성 (JSON)
 → ④ 코드가 도감 밖 운동 제거 → 화면에 표시
```

### ①② 건강 수치 해석은 코드가 한다

"체지방률이 높은가?"를 LLM에 물으면 실행할 때마다 답이 달라질 수 있다. 건강 수치라서 이건 **기준표로 고정**했다.

```ts
export function assess(m: Measurements, sex: Sex): Assessment {
  const male = sex === "M";
  const [lo, hi] = male ? [10, 20] : [18, 28];
  const pbf = m.body_fat_pct;
  const fat = pbf < lo ? "낮음" : pbf > hi ? "높음" : "표준";
  // ... BMI, 복부지방률, 근육량(골격근량 ÷ 체중)도 같은 방식

  if (fat === "높음" && muscle === "낮음") goal = "근육량 늘리기 + 체지방 줄이기";
  // ...
}
```

### ③ LLM은 "도감 운동 ID 목록 안에서" 고르기만 한다

프롬프트에는 판정 결과, 루틴 규칙 8개, **도감 운동 20개의 ID 목록**을 넣었다. 운동 목록은 도감 데이터 파일에서 자동으로 만든다.

```
## 헬스도감 운동 목록 (이 ID만 쓴다)
- chest-press: 체스트 프레스 머신 (주: 대흉근 / 보조: 전면 삼각근, 삼두근)
- leg-press: 레그 프레스 (주: 대퇴사두근, 둔근 / 보조: 햄스트링, 내전근)
...
```

답은 글이 아니라 **JSON 스키마로 강제**했다. 그래야 코드가 검사하고 화면에 쓸 수 있다.

```json
{ "id": "leg-press", "sets": 3, "reps": "10~12", "reason": "하체 큰 근육으로..." }
```

### ④ 그래도 한 번 더 코드로 거른다

```ts
const known = Boolean(getEquipmentById(ex.id));
if (!known) removed.push(ex.id);
```

프롬프트로 한 번, 코드로 한 번. **이중 방어**다.

### 결과: 62.4% → 100%

같은 모델(`gemini-3.5-flash-lite`)로, 질문 방식만 바꿔 15명에게 루틴을 받아 비교했다.

| 방식 | 도감 포함률 | 도감 밖 운동이 섞인 루틴 |
|---|---|---|
| 범용 챗봇식 ("루틴 짜 줘") | 62.4% | **15/15** |
| 제안 방식 | **100%** | 0/15 |

범용 챗봇식은 **플랭크(15명 중 13명)**, 바벨 스쿼트, 데드리프트, 덤벨 운동, 트레드밀을 추천했다. 다 좋은 운동이지만 도감에서 자세를 확인할 수 없다. 처음에 세운 문제 4가 숫자로 확인됐다.

제안 방식은 루틴 규칙(3일 구성, 하루 4~6개, 2~4세트, 8~15회, 가슴·등·하체 포함, 유산소 안내) 7개를 **15명 모두** 지켰다.

- **사진은 브라우저에서 줄여서 보낸다.** 폰 사진은 수 MB라 업로드 한도를 넘기 쉽다.
- **"사진이 Google로 전송되고 저장되지 않는다", "의료 조언이 아니다"를 화면에 명시했다.**

## 6. 실패 사례와 삽질

### 모델이 틀린 방식

| 사례 | 내용 |
|---|---|
| 막대그래프 숫자를 못 읽음 (Qwen) | 표가 아닌 그래프에만 있는 체지방률을 15장 중 7장에서 비워 냈다 |
| 헷갈리는 숫자에 속음 (Qwen) | 기초대사량 자리에 **권장섭취열량**을, 골격근량 자리에 **체중 표준범위 하한**을 넣었다 |
| 기울어진 사진에서 칸 밀림 (OCR) | 체중 칸에 지방조절값, 골격근량 칸에 체중이 들어가는 연쇄 밀림 |
| 목표가 한쪽만 반영됨 (루틴) | "근육량 + 체지방" 복합 목표 6명의 운동 82%가 12회 이상. 근육량 기준(8~12회)이 빠졌다 |

마지막 사례가 인상적이었다. **형식 검사는 전부 통과했는데 내용은 아쉬웠다.** "8~15회 안인가?"만 검사하니 한쪽으로 쏠린 걸 못 잡았다. 자동 검사가 통과했다고 끝이 아니라는 걸 배웠다.

### 무료 API의 현실

- `gemini-2.5-flash`는 새 사용자에게 **404**. 쓸 수 있는 모델 목록을 노트북에서 먼저 출력하게 바꿨다.
- 무료 등급은 **분당 5회** 제한 → 호출 간격 13초 + 429·503 자동 재시도를 넣었다.
- 최신 `gemini-3.8-flash`는 몰려서 **장당 6분 넘게** 걸렸다. 루틴 하나에 **234초** 걸린 적도 있다.
- 그래서 앱은 기본 모델이 바쁘거나 25초 안에 답이 없으면 `flash-lite`로 한 번 넘어가게 했다.

### 그 밖의 삽질

- **로컬 VLM이 `!!!!!!!!`만 출력했다.** T4 GPU에서 float16으로 돌릴 때 생기는 수치 넘침 증상으로 보인다.
- **"12~15회회"** 가 화면에 나왔다. 모델이 반복 수를 "12~15"와 "12~15회"로 섞어 보내서, 표시할 때 단위를 한 번만 붙이게 고쳤다.

## 8. 배운 점

1. **OCR과 VLM은 다른 문제를 푼다.** OCR은 "무슨 글자인가", VLM은 "이 숫자가 무슨 의미인가"까지 답한다. 결과지처럼 숫자가 빽빽한 문서는 후자가 필요했다.
2. **LLM은 범위를 좁혀 주고, 결과는 코드로 검사한다.** 판정은 코드, 구성은 LLM, 검증은 다시 코드. 이 구조 덕분에 도감 포함률 100%를 보장할 수 있었다.
3. **JSON 스키마는 AI를 서비스에 붙이는 핵심 장치다.** 글로 받으면 검사도, 화면 표시도, 자동 평가도 어렵다.
4. **실패를 숫자로 남기면 다음 할 일이 보인다.** "틀렸다"가 아니라 "71개 중 59개가 못 찾음", "82%가 12회 이상"처럼 쓰니 원인과 대응이 바로 나왔다.
5. **무료 API는 PoC에는 충분하지만 서비스에는 대비책이 필요하다.** 혼잡, 모델 교체, 한도를 전제로 설계해야 한다.
